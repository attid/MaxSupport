# Модернизация MaxSupport: дизайн

## Контекст

Проект работает на Python 3.13 и связывает MAX с Telegram через собственный
HTTP-адаптер MAX, aiogram и SQLite. Основное поведение уже покрыто unit-тестами,
но зависимости, документация и механические guardrails отстают от контракта
репозитория.

Цель модернизации — обновить весь Python-стек до последних стабильных версий,
сохранить поведение тикетов и привести репозиторий к состоянию, которое агент
может полностью проверить локально.

## Границы

В работу входят:

- обновление прямых и транзитивных Python-зависимостей;
- адаптация к актуальному aiogram;
- строгий разбор входящих MAX updates;
- корректный lifecycle HTTP-клиента, фоновых задач и SQLAlchemy engine;
- JSON-логирование в production;
- безопасная работа с временными вложениями;
- реальный единый интерфейс `just`;
- структурные тесты архитектурных границ;
- синхронизация README и документов.

Не входят:

- переход с `platform-api.max.ru` на другой домен;
- установка сертификатов для MAX;
- изменение Docker publishing;
- изменение публичного поведения тикетов, кнопок или API.

## Архитектура

Сохраняется направление зависимостей:

```text
domain <- application <- infrastructure
                      <- interface
```

Данные MAX валидируются в infrastructure-адаптере до передачи в application.
Application получает типизированное событие и не угадывает структуру внешнего
JSON. Composition root владеет ресурсами, запускает фоновые задачи и закрывает
их в `finally`.

`SupportService` разделяется только там, где это уменьшает размер и
неоднозначность без изменения публичного поведения. Новые абстракции вводятся
только при наличии конкретного потребителя или тестируемой границы.

## Ошибки и наблюдаемость

Повреждённый MAX update логируется и пропускается, не останавливая polling.
Ошибка одного update не блокирует последующие updates. Сетевые ошибки получают
существующий backoff. Логи содержат имя операции, идентификаторы и статус, но
не содержат токены и содержимое файлов.

Production использует JSON renderer. Человекочитаемый renderer допускается
только явной настройкой для локальной разработки.

## Проверка

Готовая модернизация должна подтверждаться следующими проверками:

- все прямые зависимости актуальны по `uv tree --outdated --depth 1`;
- `uv lock --check` и `uv sync --frozen` проходят;
- ruff проверяет `src`, `tests` и `.linters`;
- pytest покрывает domain, application, MAX parsing, Telegram handlers,
  repository и lifecycle;
- структурные тесты запрещают обратные импорты и циклы слоёв;
- Docker image собирается;
- рабочее дерево после форматирования остаётся чистым;
- документация соответствует фактическому коду и командам.
